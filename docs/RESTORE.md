# 数据库恢复演练

恢复工具把一份 SQLite 一致性备份还原成**全新独立数据库文件**，校验完整性和外键，不覆盖现有文件，不更改 `.env`，不自动重启或切换服务。备份和恢复文件包含账户、地址、订单及密码哈希等敏感业务数据，禁止放进网站静态目录、公开仓库或聊天附件。

## 先备份，再演练

1. 在项目目录执行 `npm run backup`（PowerShell 用 `npm.cmd run backup`），得到 `.backups/` 下带时间戳的快照。该工具通过 SQLite 备份 API 读取一致性状态，包括已提交的 WAL 内容。不要在写入期间仅复制 `.sqlite` 主文件。
2. 把备份复制至受控的异机存储，并记录访问权限、备份时间和所对应的代码版本。
3. 先在隔离测试环境恢复并验收。不要从不可信渠道下载数据库文件，也不要直接在正常运行的数据文件上试恢复。

Windows PowerShell（路径请替换为自己的实际备份文件，使用英文双引号）：

```powershell
node scripts/restore.mjs --source ".backups\自己的备份.sqlite" --destination ".restored\演练-新文件名.sqlite"
```

Linux / 宝塔项目终端：

```bash
node scripts/restore.mjs --source ".backups/自己的备份.sqlite" --destination ".restored/演练-新文件名.sqlite"
```

预构建包也可执行 `npm run restore -- --source "备份路径.sqlite" --destination "新路径.sqlite"`；PowerShell 将 `npm` 替换为 `npm.cmd`。参数必须按 `--source`、`--destination` 顺序提供，路径相对当前终端目录解析，不从 `.env` 猜测或覆盖目标。

## 工具的保护范围

- 源必须是已存在的普通 SQLite 文件；拒绝源符号链接、目录、空路径、`:memory:` 和 `file:` URI。
- 恢复前检查 SQLite 文件头、`PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`；恢复后的副本再次检查。
- 使用 SQLite 备份 API 写入目标目录下的私有临时目录，权限尽量限制为当前用户；验证后以同卷硬链接原子发布，目标已出现则拒绝，不以覆盖式重命名兜底。
- 目标文件或其 `-wal`、`-shm`、`-journal` 旁文件已经存在时拒绝；拒绝同一路径、已有硬链接、符号链接和失效符号链接。使用**独立受控目录和新文件名**，演练期间不要让其他服务同时创建这些文件。
- 临时目录自动清理。若文件系统不支持安全硬链接（某些网络共享、FAT 等），工具会失败；请选择同一台机器的受控本地 NTFS/ext4 等目录，不要改成覆盖旧文件。
- 恢复不验证备份是否来自可信运营人员、不验证备份业务时效，也不会代替账务核对。完整性通过不代表恢复到了正确日期或包含全部最近业务。

## 需要真正切换服务时

1. 确认恢复演练结果、代码版本和备份时间正确，安排维护窗口。停止本项目所有写入服务，确认没有另一实例仍在写入。
2. 对当前数据库再做一次一致性备份，保留原 `.env`、原数据库与关联日志，记录原 `DB_PATH`，确保回退路径明确。不要覆盖或删除原文件。
3. 使用全新路径恢复。人工修改 `.env` 的 `DB_PATH` 指向已验证的新文件，保留原 `ADMIN_TOKEN` 等必要配置；不要公开凭证。
4. 只启动一份服务。校验账号登录、商品库存、待付款/已付款订单、售后状态、积分与优惠券余额；确认订单时间与备份时间一致。恢复可能回退订单状态，外部支付与物流状态须另行对账，禁止盲目重发货或重退款。
5. 验收失败则停服，在确认无新写入或完成差异处理后人工恢复原 `DB_PATH`。不能在服务运行中来回切换，也不要把恢复前后的数据文件互相覆盖。

生产恢复仍需明确 RPO/RTO、异机备份保留策略和业务负责人验收。本工具及 Linux 自动测试不能替代 Windows/宝塔真实环境的恢复演练。
